# Несколько сообществ в одном репозитории

Репозиторий собирает сайты нескольких QA-сообществ на одном движке. У каждого
сообщества свои события, спикеры, страницы и картинки; шаблоны, CSS, JS,
шрифты, генератор og-обложек и все проверки — общие.

| Сообщество | Папка            | Адрес              | Деплой                      |
|------------|------------------|--------------------|-----------------------------|
| Moscow QA  | `sites/moscowqa` | https://moscowqa.ru | GitHub Pages этого репозитория |
| Piter QA   | `sites/piterqa`  | https://piterqa.ru | `MoscowQA/fork_pierqa_site`, см. «Деплой» |

## Что где лежит

```
build.py, og_images.py, sites.py   движок (общий)
templates/                         шаблоны (общие)
static/css, static/js, static/fonts  оформление (общее)
heisenbug_speakers.json,
sqadays_speakers.json              данные конференций для make sync (общие)

sites/{id}/
    site.yml                       название, город, домен, соцсети
    content/events/*.md            митапы
    content/speakers/*.md          спикеры
    content/about.md, cfp.md, organizers.md, venues.md
    static/images/logo.png         логотип (шапка, favicon, og-обложки)
    static/images/speakers/        фото спикеров
    static/images/events/          обложки событий
    templates/                     необязательно: свои версии шаблонов
```

Сборка кладёт каждое сообщество в свою папку: `dist/moscowqa/`,
`dist/piterqa/`. Сначала туда копируется общий `static/`, потом поверх —
`sites/{id}/static/`. Поэтому адреса в контенте одинаковые у всех:
`photo: "/static/images/speakers/ivan-ivanov.webp"` у спикера Piter QA
ведёт на файл `sites/piterqa/static/images/speakers/ivan-ivanov.webp`.

Спикеры не общие. Доклад в `sites/piterqa/content/events/*.md` связывается
только со спикером из `sites/piterqa/content/speakers/` — по тому же правилу
точного совпадения `name`. Если человек выступал в обоих сообществах, у него
два файла, по одному в каждом. `make sync` дописывает доклады с конференций в
оба.

## site.yml

```yaml
title: "Piter QA"            # в текстах, <title>, schema.org
brand: "PiterQA"             # рядом с логотипом, на карточках, на og-обложке
description: "..."           # meta description по умолчанию
url: "https://piterqa.ru"    # без слеша на конце; SITE_URL из окружения важнее
domain: "piterqa.ru"         # в подвале og-обложки и в UID .ics-файлов
city: "Санкт-Петербург"                 # schema.org areaServed
city_genitive: "Санкт-Петербурга"       # «QA Санкт-Петербурга»
city_prepositional: "Санкт-Петербурге"  # «митапы в Санкт-Петербурге»
since: 2026                  # «© 2026 — 2027» в подвале
links:                       # пустая ссылка — значка в подвале нет
  telegram: "https://t.me/..."
  youtube: ""
  timepad: "https://....timepad.ru"
timepad_org_id: ""           # для виджета-афиши; TIMEPAD_ORG_ID важнее
```

Обязательны `title`, `brand`, `url`, `city` — без них сборка остановится с
понятной ошибкой. Остальное имеет умолчания.

Время событий у всех считается по Москве (UTC+3): Петербург в том же поясе.
Сообщество в другом часовом поясе потребует доработать `build.py`
(`MOSCOW_OFFSET`).

## Команды

`SITE` выбирает сообщество. Без него `build`, `check`, `validate` и `sync`
проходят по всем, а команды про один сайт или файл работают с moscowqa.

```bash
make sites                           # список сообществ
make build                           # все → dist/{id}/
make build SITE=piterqa              # одно
make serve SITE=piterqa              # собрать и открыть на :8000
make validate                        # проверить все сообщества
make sync                            # доклады с конференций для всех
make sync SITE=piterqa
make photos SITE=piterqa ARGS="ivan-ivanov"
make covers SITE=piterqa
make og SITE=piterqa                 # превью обложек в og-preview/piterqa/
```

Напрямую — так же: `python3 build.py piterqa`,
`python3 scripts/validate_content.py piterqa`,
`python3 parsers/sync_heisenbug.py piterqa`,
`python3 scripts/event_cover_variants.py --site piterqa`.

## Своё оформление

Тексты шаблонов собраны из `site.yml`, поэтому новому сообществу обычно
ничего переписывать не нужно. Если всё же надо — положите файл с тем же
именем в `sites/{id}/templates/` (например, `sites/piterqa/templates/index.html`
или `.../partials/event_card.html`): он заменит общий только для этого
сообщества. Свой CSS — так же через `sites/{id}/static/css/styles.css`, но
тогда правки общего стиля придётся переносить руками, так что лучше не надо.

## Новое сообщество

1. Скопируйте `sites/piterqa/` в `sites/{id}/`.
2. Заполните `site.yml`, замените `static/images/logo.png` (квадрат, ~512px,
   PNG с прозрачностью).
3. Перепишите `content/about.md`, `cfp.md`, `venues.md`, `organizers.md`
   (и поставьте в них `updated`).
4. `make check SITE={id} && make validate SITE={id}`.

CI (`.github/workflows/ci.yml`) подхватит новое сообщество сам: тесты,
сборка и валидация идут по всем папкам `sites/*/site.yml`.

## Деплой

Pages у репозитория одна, и в этом репозитории на ней moscowqa.ru:
`.github/workflows/deploy.yml` на каждый пуш в `main`, по ночам и по кнопке
собирает и выкладывает `dist/moscowqa/`.

Остальные сообщества выкладываются из своих репозиториев — они только под
Pages. Workflow там сам забирает этот репозиторий (он публичный, ключи и
токены не нужны), собирает своё сообщество и выкладывает на свои Pages.
Шаблон этого workflow — [`deploy/community-pages.yml`](./deploy/community-pages.yml).

| Сообщество | Репозиторий Pages | Домен |
|------------|-------------------|-------|
| Piter QA   | [`MoscowQA/fork_pierqa_site`](https://github.com/MoscowQA/fork_pierqa_site) | piterqa.ru |

Выложить вручную: в репозитории сообщества Actions → Build and Deploy → Run
workflow. В поле `ref` можно указать ветку этого репозитория — например,
чтобы посмотреть на сайте ещё не влитые правки. Без него собирается `main`,
и ночная пересборка тоже идёт из `main`: правки контента Piter QA попадают на
piterqa.ru после мержа сюда, к ближайшей ночи или по кнопке.

Новое сообщество:

1. Завести репозиторий под сайт.
2. Положить в него `deploy/community-pages.yml` как
   `.github/workflows/deploy.yml`, поменять `SITE`.
3. Settings → Pages → Source: **GitHub Actions**, указать домен; DNS домена
   направить на GitHub Pages.
4. Запустить workflow вручную.

Пушить отсюда в чужой репозиторий нельзя: в организации MoscowQA отключены
deploy keys, а токен пришлось бы продлевать.

Ночная пересборка нужна каждому сообществу: прошедшее/предстоящее считается
на сборке.

## SEO

Каждое сообщество — отдельный домен со своими sitemap, robots.txt,
canonical, og-картинками и разметкой schema.org. Для поисковиков это разные
сайты, и так и задумано: у Москвы и Петербурга разные запросы («митапы
тестировщиков Москва» / «QA Питер»), разная региональность в Яндексе и
разный контент. Что сделано, чтобы сеть сайтов не мешала сама себе:

**Готовность сайта — `published` в site.yml.** Пока `false`:

* на всех страницах `<meta name="robots" content="noindex">`;
* в robots.txt нет строки `Sitemap:` (а `Disallow` не ставим: иначе краулер
  не увидит noindex и может проиндексировать голые URL);
* соседние сообщества на сайт не ссылаются — ни из подвала, ни со страниц
  спикеров.

Первое впечатление поисковика о домене — самое долгоиграющее, поэтому
выкладывать новый сайт можно сразу, а открывать — когда в нём есть хотя бы
первый митап и настоящие тексты. `make validate` при `published: true`
падает на страницах с пометкой «ЗАГОТОВКА» и предупреждает, если событий
нет.

**Пустые разделы.** Если у опубликованного сообщества ещё нет спикеров,
внешних докладов или организаторов, `/speakers/`, `/presentations/` и
`/organizers/` собираются (на них ведёт меню), но с noindex и без записи в
sitemap. Страница тем `/tags/` без докладов не собирается вовсе.

**Перекрёстные ссылки.** В подвале — ссылки на остальные опубликованные
сообщества. Если человек выступал в двух сообществах, у него два профиля на
двух доменах; это не дубль, а два разных набора докладов. Страницы связаны
явно: «Также выступает на Piter QA» для людей и `sameAs` в разметке Person —
для поисковиков. Склеиваются профили по точному `name`, как и доклады.

**Название сайта.** На главной — `Organization` (с `logo` и `alternateName`:
`brand` и всё из `alternate_names`) и `WebSite`: из них Google берёт
название сайта в выдаче, а «MoscowQA» и «Moscow QA» становятся одним и тем
же. Петербург ищут как «Питер» и «СПб» — эти слова стоят в
`seo.index_title` / `seo.index_description` Piter QA, а не размазаны по
шаблонам.

**Вручную, для каждого домена** (из репозитория это не сделать):

1. Добавить сайт в [Яндекс Вебмастер](https://webmaster.yandex.ru) и
   [Google Search Console](https://search.google.com/search-console).
   Подтверждение — мета-тегом: код в `verification.yandex` /
   `verification.google`, пересобрать и задеплоить. Или DNS-записью — тогда
   поля пустые.
2. Отправить `https://{домен}/sitemap.xml` в обе панели.
3. В Яндекс Вебмастере указать регион сайта (Москва / Санкт-Петербург) —
   без этого региональная выдача по «митапы в Питере» достаётся не сразу.
4. Завести организацию в Яндекс Бизнесе / Google Business Profile не нужно:
   у сообществ нет постоянного адреса, площадки меняются от митапа к митапу.
5. Telegram-канал и Timepad поставить ссылкой на сайт — это главные внешние
   ссылки, с которых сайт найдут.

## Общий сайт сообществ (план)

Задел под него уже есть: `load_events()`, `load_speakers()` и `load_pages()`
принимают папку контента, а `sites.load_site()` открывает любое сообщество.
Предлагаемая схема:

* `sites/{hub}/site.yml` с полем `members: [moscowqa, piterqa]` и своими
  страницами (о проекте, контакты);
* главная — ближайшие митапы всех сообществ одной лентой, с плашкой
  сообщества и ссылкой на страницу события **на сайте сообщества** (свои
  страницы событий хаб не дублирует: две копии одного митапа — это дубль
  контента для поисковиков);
* общий список спикеров: профили сообществ, склеенные по `name`, со ссылками
  на страницы на сайтах сообществ;
* общие страницы тем (`/tags/`) по докладам всех сообществ.

SEO хаба:

* страницы событий и спикеров хаб **не копирует**, а ссылается на сайты
  сообществ. Если всё же нужна своя страница митапа (например, ради ленты),
  на ней `canonical` на страницу сообщества — иначе хаб и сообщество будут
  конкурировать в выдаче одним и тем же текстом;
* разметка: хаб — `Organization` с `subOrganization` на каждое сообщество,
  а у сообществ — `parentOrganization` на хаб (добавить в `index.html`
  вместе с хабом);
* хаб получает свои запросы: «QA-митапы России», «митапы тестировщиков»,
  общий календарь — то, по чему городской сайт не ранжируется;
* в подвале сообществ ссылка на хаб появится так же, как на соседей.

Что нужно решить до реализации: домен хаба, ведёт ли он на сайты сообществ
или со временем их заменяет (тогда URL вида `/moscowqa/events/...`), и
нужны ли ему свои события (совместные конференции).
