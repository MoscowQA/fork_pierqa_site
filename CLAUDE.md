# CLAUDE.md

Инструкции для Claude Code при работе в этом репозитории.

## Что это за проект

Статические сайты QA-сообществ на одном движке: **Moscow QA**
(`sites/moscowqa/`) и **Piter QA** (`sites/piterqa/`), дальше — общий сайт
сообществ. Генератор — `build.py` (Python, Jinja2 + markdown), читает
контент из `sites/<сообщество>/content/` и рендерит HTML в
`dist/<сообщество>/`. Как устроено и как завести новое сообщество — в
[`SITES.md`](./SITES.md).

```bash
make install                 # зависимости
make build                   # собрать все сообщества в dist/<сообщество>/
make build SITE=piterqa      # только одно
make serve SITE=piterqa      # собрать и открыть на http://127.0.0.1:8000 (по умолчанию moscowqa)
make test                    # тесты (нужен make install-dev)
make validate                # проверить контент и внутренние ссылки всех сообществ
make sites                   # список сообществ
make                         # список всех целей
```

`make` — просто обёртка: `python3 build.py` и остальные скрипты по-прежнему
работают напрямую.

## Структура контента

Сначала определите, **к какому сообществу** относится правка: митап в
Петербурге — это `sites/piterqa/`, в Москве — `sites/moscowqa/`. Спикеры у
сообществ раздельные, файлы между ними не переиспользуются.

- `sites/<сообщество>/site.yml` — название, город, домен, соцсети. Тексты шаблонов собираются из него — «Moscow QA» и «Москва» в `templates/` не пишем.
- `sites/<сообщество>/content/events/{номер}-{слаг}.md` — митапы. Правила добавления/обновления — см. [`EVENT_GUIDE.md`](./EVENT_GUIDE.md).
- `sites/<сообщество>/content/speakers/{имя-фамилия}.md` — профили спикеров. Правила — см. [`SPEAKER_GUIDE.md`](./SPEAKER_GUIDE.md).
- `templates/` — Jinja2-шаблоны страниц, общие для всех. Своя версия шаблона для одного сообщества — в `sites/<сообщество>/templates/`.
- `static/` — общие CSS, JS и шрифты; картинки сообщества — в `sites/<сообщество>/static/`, на сборке они накладываются поверх общего, поэтому в контенте адреса остаются `/static/images/...`.
- `sites/<сообщество>/static/images/speakers/` — фото спикеров.

## Ключевые правила

- **Связь докладов со спикерами — по точному совпадению имени.** Значение в `talks[].speakers` в файле события должно дословно совпадать с полем `name` в `sites/<сообщество>/content/speakers/*.md`. Иначе доклад не свяжется с профилем.
- **Новый спикер → обязательно прогнать синхронизацию с конференциями.** Если для события создан новый файл в `sites/<сообщество>/content/speakers/`, сразу выполните:
  ```bash
  make sync                    # все сообщества
  make sync SITE=piterqa       # или только одно
  ```
  Это подтягивает прошлые доклады спикера с SQA Days и Heisenbug в `external_talks`. Для уже существующих спикеров повторный прогон не обязателен.
- **Темы докладов — из готового списка.** Поле `tags` в `talks[]` собирает страницы `/tags/{тема}/`. Берите теги из тех, что уже используются (список — в [`EVENT_GUIDE.md`](./EVENT_GUIDE.md)), новый заводите, только если доклад правда не попадает ни в одну тему.
- **Виджет Timepad подключается сам.** Если `registration_link` события ведёт на Timepad, кнопка «Зарегистрироваться» открывает форму регистрации поверх страницы — и на странице события, и на карточках в списках. ID вытаскивается из ссылки автоматически. Управляется полем `timepad_widget` (`popup` / `inline` / `false`), подробности — в [`TIMEPAD_WIDGET.md`](./TIMEPAD_WIDGET.md).
- **Поиск по спикерам работает сам.** На `/speakers/` есть строка поиска (`static/js/speakers-search.js`): она фильтрует карточки по имени, компании, латинской транслитерации имени (слаг файла) и названиям докладов — как митапов сообщества, так и `external_talks`. Индекс собирается в `build.py` (`speaker_search_text`), поэтому новый спикер попадает в поиск автоматически, ничего дописывать не нужно. Запрос отражается в `?q=` — ссылкой на результат можно поделиться. Без JS страница показывает полный список, как раньше.
- **Прошедшее/предстоящее считается на сборке.** Поля `completed` в front
  matter нет: `build.py` сравнивает `date` с московским «сегодня» и
  раскладывает события по спискам (`split_events`). Главная открывается
  блоком «Ближайший митап» — это первое предстоящее событие, а если впереди
  ничего нет, тот же блок показывает последний прошедший. Чтобы разбивка не
  застывала между деплоями, сайт пересобирается каждую ночь
  (`.github/workflows/deploy.yml`), а `static/js/events-status.js` поправляет
  статус на дату самого посетителя.
- **Картинка превью для ссылок рисуется сама.** У каждого события есть
  `og:image` — карточка 1200×630 с номером, датой, названием, площадкой и
  спикерами. Её собирает `og_images.py` на сборке из front matter, поэтому
  новому событию ничего дописывать не нужно. Посмотреть, не пересобирая
  сайт: `make og` (или `make og ARGS="28-black"` для одного события, `make og SITE=piterqa` для другого сообщества).
  Если у события заполнен `cover`, в превью идёт он. Подробности — в
  [`EVENT_GUIDE.md`](./EVENT_GUIDE.md).
- **Новая обложка события → прогнать `make covers SITE=<сообщество>`.** Если у события
  заполнен `cover` (или `cover_desktop`), после добавления картинки выполните:
  ```bash
  make covers                  # все обложки Moscow QA
  make covers ARGS="28-black"  # только одно событие
  make covers SITE=piterqa     # обложки Piter QA
  ```
  Рядом с исходным JPEG появятся webp-варианты на 540/768px и в полный размер,
  из них сборка соберёт `<picture>`. Исходник при этом остаётся на месте — он
  уходит в og:image, куда webp кладут не все соцсети. `make validate` ругнётся
  замечанием, если варианты забыли собрать.
- **Шрифт лежит у нас.** Inter больше не приезжает с `fonts.googleapis.com`:
  woff2 лежат в `static/fonts/inter/`, `@font-face` на них — в
  `static/css/fonts.css`, его подключает `templates/base.html`. Шрифт
  вариативный, так что все начертания 400–800 — это один файл на
  подмножество; `unicode-range` от Google остался, поэтому русской странице
  достаются только `cyrillic` и `latin` (их же `base.html` предзагружает).
  Файл `fonts.css` генерируется — руками его не правим:
  ```bash
  make fonts                   # перекачать шрифт и пересобрать fonts.css
  make fonts ARGS=--dry-run
  ```
  Ссылки на шрифт в HTML и все `url()` из `fonts.css` проверяет
  `make validate`. Подробности — в [`static/fonts/inter/README.md`](./static/fonts/inter/README.md).
  Отдельно живёт `assets/fonts/Inter.ttf` — тот же шрифт для og-обложек
  (`og_images.py`), на сайт он не уезжает.
- **Фото спикеров лежат у нас.** В `sites/<сообщество>/static/images/speakers/` для каждого спикера два webp: `{слаг}.webp` (~1080px) и `{слаг}-540.webp`; из них сборка собирает `srcset`. Внешние ссылки в `photo` не оставляем — если прислали URL, прогоните:
  ```bash
  make photos ARGS="ivan-ivanov"     # скачает, сожмёт и перепишет photo
  make photos SITE=piterqa ARGS="ivan-ivanov"   # спикер Piter QA
  make photos ARGS=--dry-run         # посмотреть, что изменится
  ```
  Отдельный файл можно сжать и вручную: `make photo FILE=sites/<сообщество>/static/images/speakers/photo.png`.
- **Правите статическую страницу — поправьте `updated`.** У страниц
  `sites/<сообщество>/content/about.md`, `cfp.md`, `organizers.md`, `venues.md` во front matter
  есть поле `updated: "ГГГГ-ММ-ДД"` — из него в `sitemap.xml` едет `lastmod`.
  У событий, докладов, спикеров и тегов эта дата считается сама (по датам
  митапов и `external_talks`), а статическую страницу датировать нечем. Не
  обновили — краулер не узнает, что текст изменился. Дату из будущего сборка
  обрезает по «сегодня»: `lastmod` — это «когда менялось», а не «когда
  будет».

- После любых правок контента запускайте `make build` и убедитесь, что сборка проходит без ошибок (проверьте счётчики событий/докладов/спикеров и тегов в выводе). `make check` дополнительно проверяет синтаксис Python и что `dist/` не пустой, а `make validate` — обязательные поля, совпадение имён спикеров, наличие картинок и внутренние ссылки. Логику `build.py` покрывают тесты: `make test`.
- **Те же проверки идут на каждый pull request** (`.github/workflows/ci.yml`): тесты, сборка и валидация контента. Если CI упал на `ОШИБКА ...` — это не формальность, а ровно тот случай, который иначе виден только на проде.
- **Сайт открывается поисковикам флагом `published` в `site.yml`.** Пока `false` — все страницы с noindex, sitemap не объявлен, соседи не ссылаются (сейчас так у Piter QA). Переключать в `true`, только когда есть первый митап и настоящие тексты: `make validate` упадёт на страницах с пометкой «ЗАГОТОВКА». Коды Яндекс Вебмастера и Search Console — в `verification`, свои заголовок и описание главной — в `seo`. Подробности — в [`SITES.md`](./SITES.md), раздел «SEO».
- **Деплоится пока только Moscow QA** (`.github/workflows/deploy.yml` выкладывает `dist/moscowqa/` на GitHub Pages). Как выкладывать остальные — в [`SITES.md`](./SITES.md), раздел «Деплой».
- `dist/` — сгенерированная директория, в git не коммитится (см. `.gitignore`).
